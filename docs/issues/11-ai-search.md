# 자연어 검색: 검색마다 부르던 LLM을 빼고, AI는 상품 태그와 등록 추천으로

## 목표

"5만원 이하 무선 마우스"처럼 말하듯이 검색하면 조건에 맞는 상품을 찾아 주는 기능입니다.

```
"5만원 이하 무선 마우스"  →  {category: MOUSE, maxPrice: 50000, keyword: "무선"}  →  DB 조회
```

지금 구조는 이렇습니다. **손님이 검색하는 순간에는 LLM을 부르지 않습니다.**

| 언제 | 누가 | 무엇을 |
|---|---|---|
| 검색할 때 | 코드 (규칙 파서 + 단어 매칭 + 오타 교정) | 띄어쓰기·조사·가격·제외어 같은 **표기 차이** |
| 상품을 등록·수정한 뒤 | AI (백그라운드 작업) | 손님이 쓸 만한 다른 표현을 **태그**로 붙임 ("초경량" 상품에 "가벼운") |
| 하루 한 번 | AI (배치) | 못 찾은 검색어를 묶어 **판매자 등록 추천** |

## 1. 처음 설계: 검색마다 LLM이 검색어를 필터로

처음에는 검색할 때마다 Gemini가 검색어를 필터로 바꿨습니다.

| 결정 | 이유 |
|---|---|
| **LLM은 질의를 필터로 바꾸기만 하고, 상품은 DB에서 조회** | 없는 상품이나 가격을 지어내는 환각이 사용자에게 보일 경로가 없음 |
| **응답 형식을 JSON Schema로 강제** (Gemini `response_format`) | 자유 텍스트를 파싱하다 실패할 일이 없음 |
| **검색어만 보내고 사용자 정보는 보내지 않음, `store: false`** | 무료 등급은 보낸 내용이 Google 제품 개선에 쓰일 수 있음 |
| **타임아웃 5초, 재시도 0회, 실패하면 규칙 기반 파서로 폴백** | LLM 장애가 검색 장애로 번지면 안 됨. 실측 응답이 0.8~2.5초라 두 배 정도 여유 |
| **Caffeine 캐시 + 스탬피드 방지** (`get(key, loader)`) | 같은 질의 20개가 동시에 와도 LLM 호출은 1번 |

답의 질은 좋았습니다. 규칙 파서가 못 하는 뜻 해석을 했습니다 (2026-11-14, gemini-3.5-flash-lite).

| 검색어 | 규칙 기반 파서 | Gemini |
|---|---|---|
| 조용히 | 키워드 "조용히" → 0건 | 키워드 "저소음" → 2건 |
| 선 없는 마우스 | 마우스 + 키워드 "선 없는" | 마우스 + "무선" → 4건 |
| 모니터 받침대 | 모니터 + 키워드 "받침대" (분류 틀림) | 액세서리 + "거치대" → 2건 |

## 2. 검색에서 LLM을 뺀 이유

2026-11-18에 같은 모델을 다시 불러 보니 **응답이 한 번에 7.5초**였습니다 (세 번 재서 7.4~7.6초). 타임아웃이 5초라, 키를 넣고 서버를 띄우면 **모든 검색이 5초를 기다린 뒤 규칙 파서로** 넘어갔습니다.

- 폴백 덕분에 검색이 멈추지는 않았습니다. 하지만 모든 검색이 5초씩 느려졌습니다.
- 앱 로그에는 `RestClientException … application/octet-stream`으로 찍혀서 응답 형식 문제처럼 보였습니다. curl로 같은 요청을 보내 보고 나서야 읽기 타임아웃인 것을 알았습니다.
- 응답 속도는 외부 서비스 사정이라 우리가 고칠 수 없고, 무료 등급은 과부하(503)도 잦았습니다 (아래 태그 작업에서 25번 중 4~5번).

그래서 **손님이 기다리는 경로에서 LLM을 뺐습니다.** 검색어를 이해하는 일은 코드가 하고(3절), AI는 기다림이 문제가 되지 않는 곳으로 옮겼습니다(4·5절). LLM 검색용 캐시·스탬피드 방지·폴백 코드는 지웠고, git 기록에 남아 있습니다.

## 3. AI보다 먼저: 검색 기본기

### 문제

검색이 상품의 이름과 짧은 설명에서 검색어를 **한 덩어리로** 찾고 있었습니다. 상세 설명에 "도서관처럼 조용한"이라고 적혀 있어도 "조용한 키보드"로는 찾지 못했고, "데스크매트"와 "데스크 매트"는 다른 말이었습니다. "마우스 패드"는 앞 단어를 보고 마우스로 분류했습니다. 결과가 0건이면 카테고리 전체를 보여 주는 완화 기능이 이런 문제를 가리고 있었습니다.

### 기준: 표기 차이는 규칙으로, 뜻 차이는 AI로

| 규칙으로 처리 (표기 차이) | AI의 몫 (뜻 차이) |
|---|---|
| 띄어쓰기 "데스크매트", 붙여 쓰기 "마우스패드", 조사·어미 "사무실에서", "조용히" | "가벼운" → 초경량 |
| 영어·줄임말 "wireless", "블투", "4K monitor" | "fps" → 240Hz |
| 가격 "5만원대", "20만원 이상 30만원 이하", "십만원 안쪽", "under 30000" | "물 튀어도" → 방수 |
| 제외 "게이밍 말고", 상품 종류 끝 글자 오타 "키보트" | "배그" → 게이밍 |

### 바꾼 것

| 무엇 | 어떻게 |
|---|---|
| 찾는 범위 | 이름·짧은 설명·**상세 설명·스펙·AI 태그**를 정규화해 합친 `search_text` 컬럼 (저장·수정할 때 만들고, 기존 상품은 마이그레이션 V7이 채움) |
| 단어 매칭 ([`SearchText`](../../backend/src/main/java/com/flashdeal/product/SearchText.java)) | 단어별로 찾고, 띄어쓰기를 무시하고 포함("패드" ↔ "장패드"). 한글 세 글자 이상은 앞 두 글자로 시작하는 단어("가벼운" ↔ "가벼움"). 한 글자("눈")는 같은 단어만 |
| 검색 순서 | 단어가 모두 맞는 상품 → 오타 교정 → **가장 많은 단어가 맞는 상품** → 카테고리·가격만으로 완화. 응답의 `match`로 어느 단계 결과인지 화면에 알림 |
| 상품 종류 | 여러 개면 맨 뒤가 중심("마우스 패드"는 패드). 좁은 종류("이어폰")는 결과에 꼭 있어야 하는 단어 |
| 군더더기 | "때", "쓸", "안" 같은 한 글자 기능어는 키워드에서 뺌 |

### 한글 오타 교정: "마으수" → "마우스"

한글을 자모로 풀어 편집 거리를 잽니다 (`마으수` → `ㅁㅏㅇㅡㅅㅜ`, `마우스` → `ㅁㅏㅇㅜㅅㅡ`: 모음 2개 차이). 오교정을 줄이려고 **결과가 0건일 때만**, **판매 중인 상품의 단어로만** 교정하고, 교정했다는 사실과 "원래 검색어로 검색" 링크를 함께 보여 줍니다.

## 4. 상품 태그: 등록할 때 AI가 "손님이 쓸 말"을 붙인다

뜻 차이("가벼운" ↔ 초경량)는 검색할 때 풀지 않고, **상품 쪽에 미리** 붙여 둡니다.

```
관리자 저장 (바로 끝남, tagged_at = null)
  → 태그 작업 (1분마다, 서버가 여러 대면 한 서버만: ShedLock)
  → Gemini: 상품 정보를 보고 태그 제안
  → 코드 검사 (아래 표)
  → 저장 직전에 상품 내용이 그대로인지 확인 → search_text에 반영
```

| 결정 | 이유 |
|---|---|
| **저장 요청 안에서 AI를 부르지 않음** | 응답이 7초 넘게 걸리기도 해서, 관리자가 저장 버튼을 누르고 기다리게 됨 |
| **실패하면 그대로 두고 다음 주기에 다시** | 무료 등급의 503 과부하가 잦음. 실제로 25개를 만들 때 4~5번 실패했고 다음 주기에 모두 채워짐 |
| **AI 응답을 기다리는 동안 DB 커넥션을 쥐지 않음** | 트랜잭션 밖에서 부르고, 저장할 때만 짧은 트랜잭션 |
| **저장 직전에 내용 비교** | AI가 답하는 7초 사이에 관리자가 상품을 고치면, 옛 내용의 태그를 저장하지 않고 다음 주기에 새 내용으로 다시 만듦 |
| **이름·설명이 바뀔 때만 다시 만듦** | 가격만 바꿨는데 AI를 부르지 않게. 새 태그가 나올 때까지는 이전 태그로 검색됨 |
| **상품은 `@DynamicUpdate`** | 태그만 바꿔도 Hibernate가 모든 컬럼(재고 포함)을 덮어쓰지 않음 ([#6](04-stock-lost-update.md)) |

### AI가 판단하고, 사실은 코드가 확인한다

사람이 승인하는 단계는 없습니다. 대신 코드가 확인할 수 있는 사실과 어긋나면 뺍니다 ([`ProductTagger.check`](../../backend/src/main/java/com/flashdeal/ai/ProductTagger.java)).

시드 상품 25개에 Gemini가 제안한 **254개 중 120개**가 남았습니다 (2026-11-19).

| 빼는 이유 | 개수 | 예 | 왜 빼나 |
|---|---|---|---|
| 이미 상품 정보에 있음 | 125 | 적축 키보드에 "적축" | 태그 없이도 찾힘. "상품 정보에 없는 말 위주로"라고 지시해도 절반은 있는 말을 줬음 |
| 가격·광고 표현 | 4 | "고성능", "전문가용", "프리미엄" | 가격은 사실이라 가격 필터의 몫. 광고 문구는 검색을 흐림 |
| 근거 없는 기능 | 3 | 연결 방식이 안 적힌 키보드에 "유선", 트랙볼에 "무소음" | 무선·방수·소음 같은 기능은 상품 정보에 근거가 있어야 함 |
| 한 글자, 너무 긴 말 | 1 | "롤" | 한 글자는 너무 흔하게 맞음 (아쉽게 리그 오브 레전드의 줄임말도 빠짐) |
| 다른 상품 종류 이름 | 1 | 키캡에 "키보드부품" | 스피커에 "헤드셋대용"이 붙으면 헤드셋 검색에 스피커가 나옴 |

뺀 말과 이유는 로그(`event=PRODUCT_TAGGED … dropped={…}`)로 남겨서 AI가 무엇을 잘못 제안하는지 봅니다.

**시드 태그는 Gemini가 제안한 말을 그대로 파일([`product-tags.json`](../../backend/src/main/resources/seed/product-tags.json))에 저장해 두고, 불러올 때 같은 코드 검사를 거칩니다.** 키 없이도 테스트와 평가가 같은 결과를 내고, 검사 규칙을 바꾸면 시드에도 바로 반영됩니다.

## 5. 판매자 등록 추천: 손님이 찾았지만 없던 상품

검색 기록(activity_log)에는 이미 검색어와 결과 수가 남고 있었습니다. 여기에 결과 상태(`match`)를 더해서, **손님이 찾았는데 못 찾은 검색**을 골라냅니다.

```
1. 못 찾은 검색 모으기 (코드)   결과 없음(NONE) · 일부만 맞음(SOME_WORDS) · 조건을 풀어서 보여 줌(RELAXED)을 검색어별로 셈
2. 묶어서 정리하기 (AI)        "물 튀어도 되는 스피커", "샤워할 때 듣는 스피커" → 방수 스피커
3. 사실 확인 (코드)            횟수는 코드가 센 값, 목록에 없는 검색어는 뺌,
                              AI가 고른 "판매자 말"로 우리 상품을 다시 검색 → 있으면 "있는데 못 찾음", 없으면 "등록 추천"
```

하루 한 번(새벽 4시, 한 서버에서만) 돌고, 관리자 화면 "등록 추천"에서 버튼으로 바로 돌릴 수도 있습니다. 손님 정보는 쓰지 않고 검색어와 횟수만 봅니다.

### 시행착오: AI가 붙인 이름 하나로는 확인할 수 없었다

실제 Gemini로 돌리면서 세 번 고쳤습니다.

| 문제 | 원인 | 고친 것 |
|---|---|---|
| 묶음이 0개 | 검색어를 "웹캠 (6)"처럼 횟수와 같이 줬더니, AI가 "웹캠 (6)"으로 돌려줘서 코드가 "목록에 없는 검색어"로 다 뺌 | 목록을 JSON(`query`, `searches` 필드)으로 주고, 끝의 "(숫자)"는 떼고 비교 |
| 콘덴서 마이크가 "있는데 못 찾음"으로, 그 상품은 **저소음 마우스** | AI가 이름을 "마이크"로 줄였고, 마우스 스펙의 "마이크로 스위치"가 "마이크"와 맞음 | AI가 고른 종류(AUDIO)와 같은 상품만 인정 |
| 배그 헤드셋이 "등록 추천"으로 (게이밍 헤드셋이 있는데) | 이름을 "배틀그라운드용 헤드셋"처럼 **손님 말**로 지어서, 우리 상품 설명과 안 맞음 | 이름(`need`, 사람이 읽을 것)과 **판매자 말**(`keywords`, 다시 검색할 것)을 따로 받음 |

손님 말을 판매자 말로 바꾸는 것(배그 → 게이밍)은 뜻 해석이라 AI의 몫이고, 그런 상품이 실제로 있는지는 사실이라 코드가 검색해서 확인합니다.

| 무소음 키보드 | 2 | 밤에 써도 가족 안 깨는 키보드 | 등록 추천 ❌ (저소음 키보드가 있음) |

8개 중 7개가 맞았습니다. 틀린 하나는 AI가 고른 판매자 말("무소음")과 우리 상품의 표기("저소음")가 달라서입니다. 같은 입력으로 전에 돌렸을 때는 "저소음 키보드"로 맞혔습니다. LLM의 답은 돌릴 때마다 조금씩 달라서, 이 결과는 **판매자가 보고 판단하는 추천**으로만 쓰고 검색에 자동으로 반영하지 않습니다.

**검색 기록은 시연용으로 만든 데이터입니다.** 실제 손님이 없어서, 시드 단계에서 검색어 18개를 실제 검색 경로로 돌리고(결과 상태는 실제 값) 기록에 `demo: true`를 남겼습니다. 화면에도 몇 건이 시연용인지 표시합니다. 이 기능은 "잘 팔릴 상품을 예측"하지 않습니다. **손님이 찾았는데 없던 것**만 보여 줍니다.

## 6. 결과

질의 72개에 시드 상품 기준 정답을 붙여 두고([`cases.json`](../../backend/src/test/resources/search-eval/cases.json)), 검색창과 같은 경로를 키 없이 돌렸습니다 (`./gradlew searchEval`). ◎는 결과가 모두 정답, △는 정답이 하나라도 포함입니다.

| 묶음 | 질의 | 처음 ◎ / △ | 검색 기본기 후 | AI 태그 후 |
|---|---|---|---|---|
| 기본 (2026-10 파서 평가셋의 질의) | 52 | 27 / 41 | 50 / 52 | **51 / 52** |
| 처음 보는 표현 (상황·느낌) | 20 | 1 / 16 | 13 / 20 | **15 / 20** |
| 전체 | 72 | 28 / 57 | 63 / 72 | **66 / 72** |

태그로 나아진 것: "가벼운 마우스"(태그 "가벼운"), "fps 할 때 쓸 모니터"(태그 "fps"), "게임할 때 쓸 가벼운 마우스". 나빠진 질의는 없습니다.

남은 △ 6개는 태그로 풀기 어려운 것들입니다. "배그"는 AI가 태그로 떠올리지 않았고, "밤", "물"은 한 글자라 태그 검사에서 빠지며, "막아주는", "화면 큰"은 미리 맞히기 어려운 표현입니다. **태그는 손님이 쓸 말을 미리 맞히는 방식이라 한계가 있고, 그래서 실제로 못 찾은 검색을 모아 보는 5절이 필요합니다.** 이 중 "배그", "물 튀어도", "밤에 가족 안 깨는", "주변 소리 막아주는"은 실제로 등록 추천 화면에 "있는데 못 찾음"으로 나왔습니다.

**이 숫자의 한계**: 정답은 고치기 전에 정했지만, 규칙은 이 질의들의 실패를 보면서 다듬었습니다. 태그는 평가 질의를 보지 않은 Gemini가 상품 정보만 보고 만들었지만, 이 72개가 엄밀한 의미의 처음 보는 질의는 아닙니다. 규칙을 만든 사람이 보지 않은 질의로 다시 재는 것이 다음 단계입니다.
