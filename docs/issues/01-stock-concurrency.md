# 재고 100개에 수천 건이 몰릴 때: 재고 차감 전략 4가지를 MySQL에서 실측 비교

## 문제

재고 100개인 상품에 1,000명이 동시에 1개씩 주문하면 어떻게 될까요? 락 없이 구현한 첫 버전에서는 **1,000건이 전부 성공하고 재고는 35개가 남았습니다.** 100개짜리 상품을 1,000개 판 셈입니다 (MySQL, `StockConcurrencyTest`).

## 원인: Lost Update

재고 차감이 `조회 → 검사 → 차감` 세 단계로 나뉘어 있었습니다.

```
트랜잭션 A: stock = 100 조회 → 100 >= 1 확인 → stock = 99 저장
트랜잭션 B: stock = 100 조회 → 100 >= 1 확인 → stock = 99 저장   ← A의 차감을 덮어씀
```

두 건이 팔렸는데 재고는 1개만 줄었습니다. MySQL 기본 격리 수준인 `REPEATABLE READ`는 "읽기"의 일관성을 보장할 뿐, 이런 갱신 손실은 막아주지 않습니다. 나중에 커밋한 쪽이 그대로 덮어씁니다.

## 해결: 전략 4가지를 구현해서 같은 조건으로 비교

"비관적 락을 쓰면 된다"로 끝내지 않고, 대표적인 방법 네 가지를 모두 구현해서 **같은 부하에서 비교**했습니다. `StockService`에 전략 패턴으로 넣고, 개발 도구 플래그(`flashdeal.dev-tools.enabled=true`)를 켠 서버에서는 API(`PUT /api/admin/stock-strategy/{type}`)로 서버를 재시작하지 않고 바꿀 수 있게 했습니다. 기본값은 꺼짐입니다. 운영에서 열려 있으면 관리자가 초과 판매가 나는 NAIVE로 바꿀 수 있기 때문입니다. 동시성 테스트(`StockConcurrencyTest`)는 이 API 없이 서비스를 직접 호출합니다.

| 전략 | 구현 | 특징 |
|---|---|---|
| NAIVE | 엔티티 조회 후 변경 감지 | 문제 재현용 |
| PESSIMISTIC | `SELECT ... FOR UPDATE` 후 차감 | 확실하지만 모든 요청이 한 행의 락 앞에 줄을 섬 |
| OPTIMISTIC | `UPDATE ... WHERE version = ?`, 실패하면 트랜잭션 밖에서 재시도 | 충돌이 잦으면 재시도가 폭증 |
| **ATOMIC_UPDATE** (채택) | `UPDATE product SET stock = stock - ? WHERE id = ? AND stock >= ?` | 검사와 차감이 쿼리 1개, 락을 쥐는 시간이 가장 짧음 |

낙관적 락의 재시도는 반드시 **트랜잭션 바깥**에서 해야 합니다. 같은 트랜잭션 안에서 다시 시도하면 이미 읽어 둔 오래된 version을 계속 보게 됩니다. 그래서 트랜잭션 경계 밖에 `OrderFacade`를 두고 거기서 재시도합니다.

## 결과

**MySQL 8 (InnoDB), HTTP 부하 테스트** — 재고 2,000 / 요청 2,000 / 동시 100. 모든 요청이 같은 재고 행을 두고 경합하도록 재고와 요청 수를 맞췄고, 같은 조건으로 두 번 측정했습니다.

| 전략 | TPS | p95 | p99 | 결과 |
|---|---|---|---|---|
| NAIVE | 106 / 137 | 2.4 / 1.6초 | 3.8 / 2.4초 | 2,000개 팔았는데 재고는 **74개만 줄어듦** |
| PESSIMISTIC | 98 / 126 | 2.3 / 1.6초 | 3.2 / 2.0초 | 정확 |
| OPTIMISTIC | **24 / 32** | **12.1 / 5.7초** | **14.0 / 6.2초** | **701 / 687건(35%)이 재고가 남았는데 실패** |
| ATOMIC_UPDATE | **110 / 133** | **1.8 / 1.4초** | **2.4 / 1.9초** | 정확 |

**H2 인메모리, 같은 조건** (디스크 커밋이 없어 절대 수치는 높고, 경향 비교용)

| 전략 | TPS | p99 | 결과 |
|---|---|---|---|
| NAIVE | 631 / 674 | 395 / 238ms | 재고 316 / 252개 남음 |
| PESSIMISTIC | 643 / 746 | 253 / 254ms | 정확 |
| OPTIMISTIC | 416 / 454 | 1,281 / 1,038ms | 재고가 남았는데 1 / 2건 실패 |
| ATOMIC_UPDATE | 726 / 726 | 317 / 274ms | 정확 |

**JUnit 동시성 테스트** (`StockConcurrencyTest`, 재고 100 / 요청 1,000 / 스레드 64, MySQL)

| 전략 | 성공 | 남은 재고 | 초과 판매 | 재고가 남았는데 실패 |
|---|---|---|---|---|
| NAIVE | 1,000 | 35 | **935** | 0 |
| PESSIMISTIC | 100 | 0 | 0 | 0 |
| OPTIMISTIC | 100 | 0 | 0 | **20** |
| ATOMIC_UPDATE | 100 | 0 | 0 | 0 |

> 측정 환경: 로컬 Windows 노트북, MySQL 8.0.44 기본 설정(`innodb_flush_log_at_trx_commit=1`), 인증·멱등성 처리·활동 로그를 포함한 전체 HTTP 경로. 서버 한 대 기준이라 절대 수치보다 같은 조건에서의 상대 비교로 봐야 합니다.

### 해석

- **낙관적 락은 인기 상품에서 무너집니다.** 충돌하면 트랜잭션 전체를 다시 실행하는데, MySQL에서는 재시도마다 디스크 커밋 비용까지 들어서 처리량이 1/4로 떨어지고, 재시도 한도를 넘긴 주문의 35%가 **재고가 남았는데도 실패**했습니다. 사용자 입장에서는 "품절도 아닌데 주문이 안 되는" 상황입니다. H2에서는 실패가 1~2건이라 대수롭지 않아 보였는데, 실제 DB에서 문제의 크기가 드러났습니다. 그래서 낙관적 락은 충돌이 드문 곳(주문 상태 변경)에만 `@Version`으로 씁니다.
- **락이 없을 때도 MySQL에서 훨씬 심각했습니다.** 트랜잭션이 느릴수록 같은 값을 동시에 읽고 덮어쓰는 겹침이 늘어나서, 2,000개를 팔고도 재고는 74개만 줄었습니다.
- **원자적 UPDATE와 비관적 락**: 두 번 모두 원자적 UPDATE가 처리량이 6~12% 높고 p99가 짧았습니다. 쿼리가 1개(비관적 락은 `SELECT FOR UPDATE` + `UPDATE` 2개)라 락을 쥐고 있는 시간이 짧기 때문입니다. 차이가 크지는 않아서 "압도적으로 빠르다"보다는 "더 단순하고 약간 빠르다"가 정확합니다.

## 측정 설계를 다시 한 이야기

처음에는 재고 100 / 요청 2,000으로 H2에서 **한 번만** 측정했고, 원자적 UPDATE가 비관적 락보다 55% 빠르다는 결론을 냈습니다. 같은 조건으로 다시 돌려 보니 순위가 뒤집혔습니다.

1. JVM이 워밍업되면서 뒤에 측정한 전략이 유리했습니다.
2. 2,000건 중 1,900건이 품절로 바로 끝나서, **실제 경합은 거의 측정하지 못하고 있었습니다.**

그래서 재고를 요청 수만큼 늘려 모든 요청이 경합하게 바꾸고, 본 측정 전에 워밍업을 한 번 돌리고, 같은 조건으로 두 번 측정하고, 실제 MySQL에서도 다시 쟀습니다. 위 표는 그렇게 다시 잰 결과입니다.

## 왜 Redis 분산락을 쓰지 않았나

재고가 **단일 DB의 한 행**에 있으므로 DB 행 락만으로 원자성이 보장됩니다. Redis 락을 추가하면 네트워크 홉이 하나 늘고, Redis와 DB 사이의 정합성이라는 새 문제가 생기고, 락 만료나 GC pause 같은 장애 지점이 늘어납니다. 분산락은 DB 밖의 자원을 조율해야 할 때 쓰는 도구라고 판단했습니다.

DB가 한계에 도달한다면, 다음 단계는 락을 더하는 것이 아니라 **Redis `DECR`로 재고 게이트를 앞단에 두고 DB에는 비동기로 반영**하는 구조라고 봅니다.

## 데드락 예방

여러 상품을 한 번에 주문하면 트랜잭션 A는 (1 → 2), B는 (2 → 1) 순서로 락을 잡다가 데드락이 날 수 있습니다. 주문 품목을 **productId 오름차순으로 정렬**해서 락을 잡는 순서를 통일했습니다.
