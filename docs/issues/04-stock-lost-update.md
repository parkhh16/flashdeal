# 관리자 작업이 재고를 되돌리거나 부풀리는 문제

주문 쪽 동시성만 챙기다 보면 놓치기 쉬운 곳이 관리자 기능이었습니다. 관리자 작업도 주문과 같은 재고 행을 건드립니다.

## 1. 상품 수정이 재고를 되돌림 → `@DynamicUpdate`

### 문제

관리자가 상품 수정 화면을 열어 둔 사이 주문이 들어와 재고가 10 → 7이 됐다고 해 봅시다. 관리자가 상품명만 고쳐서 저장하면, 재고가 **다시 10으로 돌아갑니다.**

### 원인

JPA 변경 감지는 기본적으로 **엔티티의 모든 컬럼**을 UPDATE합니다. 수정 트랜잭션이 읽어 둔 `stock = 10`이 상품명과 함께 그대로 다시 쓰입니다.

### 해결

- 상품 엔티티에 `@DynamicUpdate`를 붙여 **바뀐 컬럼만 UPDATE**하게 했습니다.
- 재고는 상품 수정 폼에서 아예 빼고, 원자적 UPDATE를 쓰는 전용 API로만 바꾸게 분리했습니다.

테스트에서 어노테이션을 잠시 빼고 돌려 보면 실제로 재고가 7 → 10으로 되돌아가는 것을 확인할 수 있습니다 (`AdminFeaturesTest.adminEditDoesNotOverwriteStock`).

## 2. 한정 100개 상품의 재고가 16,602개가 된 이유 → 덮어쓰기 대신 증감

### 문제

MySQL로 하루 동안 데모 서버를 돌린 뒤 보니, **한정 100개 상품의 재고가 16,602개**가 되어 있었습니다. 실제 서비스였다면 실물보다 훨씬 많이 팔 수 있는 상태입니다.

### 원인

- `product.stock`은 "지금 팔 수 있는 가용 재고"이고, **결제 대기 주문이 쥐고 있는 수량은 이미 빠져 있습니다.** (주문 시점에 재고를 선점하고, 10분 안에 결제하지 않으면 돌려받습니다. → [재고 선점과 TTL](07-stock-reservation.md))
- 부하 테스트를 준비하면서 관리자 API로 재고를 `stock = 2000`처럼 **덮어썼는데**, 그 순간에도 결제 대기 주문 수천 건이 재고를 쥐고 있었습니다.
- 10분 뒤 그 주문들이 만료되며 쥐고 있던 수량을 **덮어쓴 값 위에 다시 더했고**, 이게 여러 번 반복되며 재고가 부풀었습니다.

만료된 주문 수(16,602건)와 재고 수가 **정확히 같았던** 덕분에 원인을 확정할 수 있었습니다.

### 해결

관리자 재고 조정을 **"몇 개로 바꾼다"(덮어쓰기)에서 "몇 개 들어왔다/나갔다"(증감)** 로 바꿨습니다.

```sql
UPDATE product SET stock = stock + :delta WHERE id = :id AND stock + :delta >= 0
```

- 원자적 UPDATE라서 같은 순간 들어온 주문의 차감과 섞여도 둘 다 반영됩니다.
- 쥐고 있던 수량이 나중에 돌아와도 실물 수와 어긋나지 않습니다. 잔액을 `balance = balance + amount`로 갱신하는 것과 같은 원리입니다.
- 관리자 화면에는 **가용 재고와 결제 대기 주문이 쥔 수량을 따로** 보여줘서, "팔 수 있는 수"와 "돌아올 수 있는 수"를 헷갈리지 않게 했습니다.

테스트로 확인한 차이:

```
실물 10개, 결제 대기 주문이 3개를 쥐고 있음 → 가용 7
관리자가 5개 입고

증감:     가용 7 + 5 = 12 → 결제 대기 3개가 돌아옴 → 15  (실물 15개와 일치)
덮어쓰기: 관리자가 실물 수 15 입력 → 15 → 결제 대기 3개가 돌아옴 → 18  (실물보다 3개 많음)
```

부하 테스트도 더 이상 기존 상품의 재고를 덮어쓰지 않고, **실행할 때마다 전용 상품을 새로 만들고 끝나면 판매 중지**합니다.
