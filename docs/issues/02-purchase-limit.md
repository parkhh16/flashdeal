# 1인 구매 제한: 락을 걸었는데도 뚫린 이유

"1인 2개" 같은 구매 제한을 만들면서 세 번 막혔습니다. 마지막 문제는 H2에서는 드러나지 않고 MySQL로 옮기고 나서야 보였습니다.

## 1. check-then-act 경쟁 → 사용자 행 락

구매 제한 검사는 `지금까지 산 개수 조회 → 한도와 비교 → 주문 생성` 순서입니다. 같은 사용자가 버튼을 여러 번 빠르게 누르면 요청 여러 개가 동시에 "아직 0개 샀다"를 읽고 모두 통과합니다.

→ **사용자 행에 락**(`SELECT ... FOR UPDATE`)을 걸어 **같은 사용자의 주문만** 줄을 세웠습니다.

- 락 범위가 상품이 아니라 사용자라서, 인기 상품 하나에 모든 요청이 몰리는 핫스팟이 생기지 않습니다.
- 락 순서가 항상 `사용자 → 상품(id 오름차순)`이라 데드락이 생기지 않습니다.
- 구매 제한이 걸린 상품을 주문할 때만 락을 잡습니다.

## 2. 영속성 컨텍스트가 숨긴 옛날 재고 → DTO 프로젝션

구매 제한과 판매 기간을 검사하려고 상품을 먼저 **엔티티로** 읽었더니, 이어지는 `SELECT ... FOR UPDATE`가 최신 재고가 아니라 **먼저 읽어 둔 옛날 재고**를 돌려줬습니다.

Hibernate는 영속성 컨텍스트에서 이미 관리 중인 엔티티를 쿼리 결과로 덮어쓰지 않습니다. 락은 최신 행에 걸리지만, 코드가 보는 값은 캐시된 엔티티의 값입니다. 비관적 락 전략에서 초과 판매가 다시 생길 수 있는 구조였습니다.

→ 검증에 필요한 값(판매 기간, 1인 제한, 판매 여부)만 **DTO 프로젝션**(`PurchaseRule`)으로 읽도록 바꿨습니다. 프로젝션은 영속성 컨텍스트에 들어가지 않습니다.

## 3. MySQL에서만 뚫린 이유: REPEATABLE READ 스냅샷 → READ COMMITTED

H2에서 통과하던 테스트를 MySQL에서 돌렸더니, **한도가 2개인데 동시 요청 10개 중 4개가 성공**했습니다. 사용자 행 락까지 걸었는데도요.

### 원인

MySQL 기본 격리 수준인 `REPEATABLE READ`는 트랜잭션의 **첫 번째 일반 SELECT 시점에 스냅샷을 고정**하고 끝까지 그 스냅샷을 씁니다. 주문 흐름은 이랬습니다.

```
[상품 규칙 조회]         ← 여기서 스냅샷이 고정됨
[사용자 행 락 대기]       ← 앞 사람이 주문을 커밋하고 락을 풂
[지금까지 산 개수 조회]   ← 락은 얻었지만, 고정된 옛 스냅샷을 읽음 → 앞 사람의 주문이 안 보임
```

락은 최신 상태에서 얻었지만, 개수는 **락을 기다리기 전의 스냅샷**에서 세고 있었습니다. H2는 문장마다 최신 커밋을 읽기 때문에(READ COMMITTED처럼 동작) 드러나지 않았습니다.

### 해결

주문 생성 트랜잭션만 `@Transactional(isolation = READ_COMMITTED)`로 명시했습니다. 읽을 때마다 최신 커밋을 보므로 락 이후의 조회가 정확해집니다. Oracle과 PostgreSQL의 기본값이기도 합니다.

다른 방법으로 ① 조회 순서를 바꿔 락을 먼저 잡거나, ② 개수 조회를 잠금 읽기(`FOR SHARE`)로 바꾸는 것도 검토했습니다. 둘 다 "이 순서로 코드를 써야만 맞다"는 암묵적인 규칙에 기대게 돼서, 격리 수준을 명시하는 쪽을 골랐습니다.

## 결과

- 같은 사용자가 1개씩 10번 동시에 주문해도 **한도(2개)만큼만 성공** (H2, MySQL 모두)
- 만료된 주문은 재고를 돌려받았으므로 한도 계산에서 제외
